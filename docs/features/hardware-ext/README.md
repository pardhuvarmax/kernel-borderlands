## Hardware Extensions for KB Project: [NOMAD](https://github.com/pardhuvarmax/the-nomad)

- [`nomad-hardware-appliance.md`](nomad-hardware-appliance.md) — **Proposed, not implemented (v0.2).** Node Out-of-Band Module for Attestation & Defense: a physically independent appliance (SBC + STM32 safety controller + ESP32 comms processor + TPM root of trust + relay fencing) that supervises and attests Kernel Borderlands from outside the host's trust boundary, addressing the one failure mode software-only same-host watchdogging can't structurally cover: total kernel compromise. Continues `kb-checker`'s external-watchdog role but is scoped as its own future subsystem, not a `kb-checker` extension. Includes an updated bench-buildable bill of materials, a production-appliance concept, and cluster-support direction (future work, detailed in `nomad-fms.md`); §14 now tracks Resolved vs. Still Open — failure semantics, the recovery-stage relationship to `kb-checker`'s existing chain, and the TPM integration point are resolved (the last one detailed in `nomad-rootkit-resistance.md`), repo placement/wire protocol/internal SBC↔STM32↔ESP32 protocol remain open. Supersedes the earlier `kbc-hardware-watchdog.md`.
- [`nomad-fms.md`](nomad-fms.md) — **Proposed, not implemented.** Fabric Management Service: the fleet-orchestration sub-service of NOMAD, expanding its "Cluster Support" section into a Fabric → Colony → Family → Node hierarchy with discovery, policy inheritance, health monitoring, event aggregation, cross-host correlation, and recovery coordination. Explicitly scoped to come *after* a working single-host NOMAD prototype, not before. Resolved (see `nomad-hardware-appliance.md` §3.1): FMS is classified non-security-critical under a Local Autonomy Principle (every node protects itself with zero dependency on FMS) and communicates only over a separate Fabric Management Plane (dedicated VLAN/NIC, signed summaries only) that structurally cannot reach the OOB Trust Plane used for attestation/recovery — closing what were previously two open risks. Cross-host correlation ownership and the fleet wire protocol remain open.
- [`nomad-cheap.md`](nomad-cheap.md) — **Proposed, not implemented (alt.).** Cost-reduced BOM appendix to `nomad-hardware-appliance.md`'s Model B shared-chassis build — swaps in cheaper parts (Pi Zero 2 W, bare ESP32/STM32 modules, shared relay board, dropped display) that don't touch NOMAD's threat model, tags each as "free" or "trade-off." Brings a Pentagon (5-host) chassis from $234–$383 down to $114–$168, ~$11–$17 per person for a 10-person team. Explicitly rejects the one trade-off that looked biggest on paper — discrete TPM → firmware TPM (§3.7): not practically free on a Pi-based chassis (needs an unproven OP-TEE/TPM2 port), only genuinely free on an Intel N100 SBC, and even there weakens the design's hardware-rooted trust guarantee for a saving of just $4–$8 per host. Does not change architecture, threat model, or `nomad-hardware-appliance.md`'s open questions — pricing only.
- [`nomad-expense.md`](nomad-expense.md) — **Costing exercise only.** Consolidated per-person expense breakdown combining the reference and cost-reduced BOMs from the two docs above for 10- and 15-member teams — not a build target or sourcing quote.
- [`nomad-rootkit-resistance.md`](nomad-rootkit-resistance.md) — **Proposed, not implemented.** Resolves `nomad-hardware-appliance.md` §14 Open Question 4 (TPM integration point) and answers the sharpest question the whole design invites: what if `kb-checker` itself is compromised, not killed, but alive and lying? Two separate TPMs, two separate jobs — NOMAD's own (unchanged) plus the *host's own*, already-present TPM 2.0, holding `kb-checker`'s OOB signing key sealed to the host's own measured-boot chain via `TPM2_PolicyPCR`, so a rootkit that loads a new kernel module invalidates the seal permanently until reboot. Layers on memory-corruption-exploitation narrowing (ASLR/KASLR, W^X, stack canaries, `kexec`/`devmem` lockdown, LKRG in report-only mode), cross-vantage/canary/timing checks for what survives PCR-sealing, and a three-bucket failure classification (silence / cryptographic failure / content implausibility) so a fencing event becomes actionable evidence, not a generic alarm. Includes a runnable `tpm2-tools` demo (PCR 16 sandbox) exercised live on real hardware. Honest throughout about what it does and doesn't close — see its own §11/§12.
