# Changelog

All notable changes to the **Kernel Borderlands** project are documented below.

---

## [1.1.0] - 2026-10-29

Hardening release on top of 1.0.0: the sensor can no longer flood the journal or restart without bound, swarm "quarantine" now really enforces, the live agent pipeline exists, and the learned policies are gated off until they are retrained on sensor data. Version bumped to 1.1.0 in `packaging/arch/PKGBUILD`, `packaging/deb/build-deb.sh`, the `kbd` banner and the field-manual sources; **the field-manual PDFs in `dist/` were not rebuilt** (no LaTeX toolchain run; the sources carry the new file names). `dist/` holds the 1.1.0 Arch package (built on Arch) and `.deb` (built on the Ubuntu 24.04 dev VM, glibc 2.39), with `SHA256SUMS`; the 1.0.0 packages were removed from `dist/`. The `.deb` is installed on the dev VM (sensor unit left masked, `kb-checker` still held down). Packaging fixes found while building: script exec bits were committed as `100644` (dpkg-deb rejected `postinst`), and `make install-pkg` did not ship `kb-aads/features` and `kb-aads/pipeline` (the installed `kbagents` would have failed on import); a manifest test now covers the latter. `libbpf/` is not tracked in git and must be present beside `kb-core/` to build. **The 1.1.0 packages are no longer tracked in git** (each rebuild added ~42 MB of incompressible history; six of them were removed from the unpushed history, ~267 MB): `dist/` keeps them on disk, ignored, with `SHA256SUMS` and the manuals tracked; publish the `.deb` and `.pkg.tar.zst` as GitHub Release assets and verify them against `dist/SHA256SUMS`. **Upgrade note:** installing any package older than 1.1.0 over this one brings back the per-event sensor logging and the unbounded restarts. Verified and not verified items are listed per entry below.

### Entries for 1.1.0 (2026-10-29)

Hardening pass: live agent pipeline, enforcement correctness, flood behaviour. Nothing here was run against a live sensor (needs root); Go and sensor-build results are below each item. Manuscript untouched.

### Fixed
- **Swarm "quarantine" enforced nothing** (`kb-control-plane/internal/controlplane/grpc.go`, `kb-aads/agents/executor.py`): the Executor's only action was `QUARANTINE`, which `SubmitAgentDecision` did not enforce, yet it audited `AGENT_QUARANTINE` and replied `success: true, "executed"`. `kbd` now rejects any action that is not `TERMINATE`/`NAMESPACE`/`SECCOMP`/`CGROUP` (`success: false`, nothing audited as executed). The Executor sends real levels, staged `CGROUP` -> `SECCOMP` -> `NAMESPACE` -> `TERMINATE` up to the decided level, paced for kbd's 200 ms per-agent throttle (throttle replies retried, any other refusal halts the ladder). `execute_quarantine` is kept as a name that stages to the payload's level. Tests: unknown action rejected and not audited; a `CGROUP` decision puts the right pid/level frame on the sensor socket (`grpc_test.go`).
- **Containment ack no longer rides the telemetry socket** (`kb-core/userspace/sensor/kbd_sensor.c`, `docs/development/core-control/wire-protocol.md`): the sensor now writes `CONTAINMENT_ACK` back on `kbct.sock`; under a telemetry flood a non-blocking ack write on `kbd.sock` could fail and also tore that connection down. Frame and `KB_WIRE_VERSION` unchanged; `kbd` handles the ack on either listener. A missing ack is still "unknown", never "applied" (no kill). Sensor builds in a scratch copy; not exercised against a running sensor.

- **Sensor skips its own syscall samples in the kernel; every other self event is reported and logged as CRITICAL** (`kb-core/ebpf/kbd_sensor.bpf.c`, `userspace/sensor/kbd_sensor.c`): on a busy host the sensor's own syscall traffic (tens of thousands/s of map scans, `/proc` reads, journal writes) kept the syscall-sampling hook and its rate limiter busy and produced a stream of "telemetry dropped" (type 10) markers attributed to the sensor, ~90% of the events reaching userspace in one measured window and 36-76% of a core. `kb_self_tgid` (a `const volatile` set from `getpid()` before load) makes **only `kb_handle_syscall`** return early for the sensor's thread group, before its count maps, rate limiter and ring buffer; skipped syscalls are counted in a per-CPU map and reported in the 30 s summary. **All other hooks still report the sensor like any process** (sensitive file opens, exec, connect/bind, executable memory, credential changes, cross-process writes, capability probes) and the `lsm/*` enforcement hooks are unchanged: the sensor never legitimately does those, so userspace now prints a `[SENSOR][CRITICAL] activity by the sensor process itself ...` line (max 5/s, remainder counted in the summary) regardless of `KB_SENSOR_VERBOSE`, and still scores/reports the event to `kbd`. (A first version dropped *all* self telemetry; that would have hidden a hijacked sensor and was replaced before release.) Verified on the Ubuntu 24.04 dev VM under `unattended-upgrades` load: sensor CPU 36-76% of a core -> <1%, own events reaching userspace 1,174 per 30 s -> 0, verifier accepts the program, 0 CRITICAL lines in normal operation, and a simulated hijack (`gdb` making the running sensor `open("/etc/shadow")`) produced the CRITICAL line. Not tested: a simulated outbound `connect()` or executable-memory mapping by the sensor (those hooks are unchanged and not self-filtered), and `kbd`-side handling of a hot sensor PID (the sensor is CPM-protected, so containment of it is refused and audited).
- **Attack-lab smoke test #2 (observe-only on `kbd`, `KB_SENSOR_EXIT_STATE=all`): the short-lived-process problem is solved, and the corpus exposes real detection findings** (dev VM, temporary drop-ins removed automatically and verified gone afterwards): 10,183 events, 0 stream gaps, audit export now works. Attribution: 209 events, up from 134 (run 1) and 33 before the ppid fix; every execution except two now has observations (`benign_compile` 0 -> 28 events / 28 processes incl. `gcc`, `cc1`, `as`; `credential_access` 38; `privilege_escalation` 80; `benign_admin_privileged` 59). 342 exit states sent, 0 rate-limited. Most of the capture (9,974 of 10,183 events) is background desktop activity, as designed. **Findings the evaluation must address (not fixed):** (1) the **hard negative** `benign_admin_privileged` (legitimate `sudo tar /etc`, `systemctl status`) reaches SUSPICIOUS in 11 zone transitions with a higher peak score (28.5) than the `credential_access` attack (21.8, 10 transitions): the current rules cannot tell legitimate privileged administration from credential theft, a baseline false-positive rate for the fixed policy; (2) `process_injection` and `memory_exploit` each produced only 2 observations and stayed SAFE (peaks 21.1 and 13.1), although the specification puts `process_vm_writev` injection in BORDERLANDS: either the sensor misses them or the payloads do not issue the intended syscalls; **the payloads need verifying with `strace` before a full capture**. Not done: a full-size capture, payload verification, repeated trials.
- **First baseline comparison on the corpus** (`scripts/attack-lab/baselines.py`, report in `datasets/attack-lab/20261031T183320/baselines_report.txt`): the sensor's fixed rule engine vs logistic regression and a gradient-boosted tree on schema-v1 features only (asserted identical to `features/schema.py`), execution-level split with `evasion` and `admin_privileged` held out entirely, thresholds chosen on the training split only (<= 0.1% of benign+background rows flagged), judged per execution. **Descriptive only: 15 attack + 15 benign test executions, intervals are wide (95% Wilson in the report), all systems share the same sensor features.** Findings: (1) the fixed rule `zone >= SUSPICIOUS` flags 11/15 attacks and 5/15 benign executions (all the `admin_privileged` hard negatives) and about **14 distinct background desktop processes per minute** (the alert noise on a normal Ubuntu desktop); `zone >= BORDERLANDS` flags 2/15 and 0/15 with 0.24 processes/min. (2) A logistic regression reaches the same recall (12/15) with the same 5/15 benign flags at **0.64 background processes/min, roughly 22x less noise** than the SUSPICIOUS rule. (3) The gradient-boosted tree catches 15/15 attacks (including `network_c2` and `memory_exploit`, which the rules miss, but only 2 test executions each) at the cost of 9/15 benign flagged (also `idle` and `admin`) and 9 background processes/min; the ablation without `zone`/`score` behaves the same, so the dimension scores alone carry similar signal. (4) **No system, rule or learned, separates the `sudo tar /etc` hard negatives from credential theft**: all non-BORDERLANDS systems flag all 5. That points at missing features (parent/session context, sensitive-file counts, event sequence), not at the model class. Not shown: any claim beyond this host, this corpus size, or this feature set; the PPO policies were not evaluated (they are refused by the live path until retrained on this schema).
- **Attack-lab: first full corpus (60 executions) captured, analysed and exported** (`scripts/attack-lab/{analyze,export}.py`; data in `datasets/attack-lab/<run_id>/`, not tracked in git): 12 scenarios x 5 repeats on the dev VM with `kbd` in observe-only mode and `KB_SENSOR_EXIT_STATE=all` (temporary drop-ins removed automatically and verified gone), 246,114 events, 0 stream gaps, no watchdog trip, load never above 0.61, every execution with attributed events. Fixed-rule-engine baseline (descriptive, n=5 per family, 95% Wilson intervals in `analysis_report.txt`): attacks reaching SUSPICIOUS or higher 20/30, BORDERLANDS 5/30 (only `process_injection`); benign executions flagged SUSPICIOUS 5/30 (all `admin_privileged`); first zone audit a median 3 ms (max 213 ms) after the first malicious action. Not flagged at all: `network_c2` and `memory_exploit` (0/5 each; plain RWX is gated by design, and the beaconing detector did not fire: cause not established). The rule engine is per process, so a multi-process attack (each step in a new short-lived child) never accumulates evidence in one state machine. `export.py` writes CSV, Parquet and Excel (.xlsx) tables (events, executions, kbd audit, proposed train/test split with `evasion` and `admin_privileged` held out) plus the raw files and a data dictionary; columns `label_*` and `split` are ground truth and must never be features. 5 repeats per family is far too few for performance claims.
- **Detection fixes from the attack-lab findings** (decisions taken with the operator after the docs were found to contradict each other): (1) **Cross-process injection is detected from a clean process.** `docs/specifications/kernel_borderlands_specification.md` says `OBSERVED --> BORDERLANDS : Memory Injection (process_vm_writev)` (and its `shellcode_injection` sample rule has `min_source_state: SAFE`), but the code, and the lower-precedence `behavior-engine.md`, required the process to be SUSPICIOUS first, and a one-level-at-a-time safety clamp in `kb_behavior_evaluate()` blocked even the spec's own two-level edge; a clean injector stayed zone SAFE. Now `proc_mem_write_borderlands` is a documented direct promotion (any state -> BORDERLANDS) and the clamp exempts rules declaring `min_source_state + 1 < target_state` (in the shipped rules only that one and `known_ioc_sequence`); `rwx_memory_abuse` is RWX-only and still needs SUSPICIOUS first, so JITs and browsers do not trip it. Both rule copies changed (`kb_rules.c`, `kb-control-plane/config/rules.yaml`), `behavior-engine.md` updated, 3 new behavior-engine tests (clean injector -> BORDERLANDS; plain RWX from a clean process -> not; RWX from a suspicious process -> yes), 4 existing ones unchanged. **Consequence to know:** BORDERLANDS applies the automatic throttle, so debuggers and CRIU doing `process_vm_writev` will now trigger it (use the allowlist). (2) **`allowlist.yaml` is now read by `kbd`** (`--allowlist`, installed to `/etc/kb/allowlist.yaml`, a conffile, re-read on `kbctl policy reload`): listed comm names are exempt from AUTOMATIC containment only. Because comm is chosen by the process, an entry is honoured only if `/proc/<pid>/exe` resolves under `/usr/bin`, `/usr/sbin`, `/bin`, `/sbin`, `/usr/lib/systemd`, `/lib/systemd` or `/usr/libexec`; a process that spoofs the name from `/tmp`, has exited, or whose binary was deleted is NOT exempt (fails closed). **Hardened after review:** checking only the directory left a hole (`/usr/bin/python3` renaming its own comm to `sshd` via `prctl(PR_SET_NAME)` passed), so an entry is now bound to the binary it names (the executable's basename must equal the allowlisted comm at comm's 15-byte limit, or the entry's optional absolute `path:` must match exactly) and the file must be root-owned and not group/world-writable; tests added for the renamed-trusted-binary, not-root-owned and name-binding cases. The zone is never rewritten: `zone_transition` events keep the true zone and carry `allowlisted=<reason>`, and an `ALLOWLIST_EXEMPT_<ACTION>` audit entry is written whenever it applies. Tests: spoofed comm from `/tmp`, unresolvable process, trusted binary (suppressed, audited, tagged), YAML handling. The shipped default stays at `systemd` and `sshd`: names like `cat`, `tar` or `python` cannot safely be listed, so the **hard-negative false positives (`sudo tar /etc`) are not removed by this**; they remain the baseline the retrained policy must beat. **A regression this exposed, found by the VM verification and fixed before release:** the sensor treated every memory event with `addr == 0 && rwx` as a cross-process write, but an ordinary anonymous RWX `mmap` also has `addr == 0` (the address hint), so plain RWX mappings were tagged `PROC_MEM_WRITE` instead of `RWX_MAPPING`; harmless while both needed SUSPICIOUS, but with the new direct promotion every JIT (browsers, Java, Node) would have been thrown into BORDERLANDS and throttled (the `memory_exploit` lab run did exactly that). `include/kb_memclass.h` now separates them (only the `process_vm_writev` marker, `prot == 0`, is a cross-process write); as a side effect `RWX_MAPPING` is now set correctly, which `known_ioc_sequence` (exec -> outbound -> RWX) needs. Test added (`test_memory_event_classification`). **Verified on the dev VM with `kbd` protection ON** (`--allow-containment`, no observe-only): `process_injection` (clean process, `process_vm_writev`) now goes `SAFE -> BORDERLANDS` and `kbd` applies the CGROUP throttle (it stayed SAFE before); `memory_exploit` (plain RWX only) stays SAFE with no throttle; `credential_access` and the hard negative are unchanged (SUSPICIOUS). **Not verified:** the false-positive rate with a populated allowlist; JIT-heavy real applications (browsers, Java) against the new rules; `ptrace`-only injection (still needs SUSPICIOUS first, per `behavior-engine.md`).
- **Sensor publishes a final `process_state` when a process exits** (`kb-core/userspace/sensor/kbd_sensor.c`): `kbd` only learned a process's state at every 20th event or on a zone change, and the exit message was not republished as a `process_state`, so short-lived or low-activity processes (compiler children, one-shot payloads, `sudo cat`) finished without `kbd`'s event feed, the swarm or a training corpus ever seeing their score. The final state is now sent before the exit message. `KB_SENSOR_EXIT_STATE=anomalous` (default: only processes that scored >= 5 or left SAFE), `all` (every exit; for lab capture) or `off`; always capped at 2,000 per second so `kbd` cannot be flooded, with sent / benign-skipped / rate-limited counts in the 30 s summary. **Verified on the dev VM** (capped throwaway sensor units, `kbd` protection untouched): default mode surfaced the sensitive short-lived processes (`cat`, 2x `sudo`) and skipped 15 harmless `true`s; `all` mode surfaced every short-lived process (15x `true`, `gcc`, `cc1`, `as`, 4x `id`, `ls`); a process storm in `all` mode sent 41,692 and held back 137,052 exit states at the cap, with the sensor at 26% of a core, 0 dropped events, `kbd` healthy and no errors. **Not verified:** a repeat of the attack-lab smoke test with this build (it needs the operator to re-approve observe-only), and long-run behaviour.
- **Attack-lab first real capture on the VM: pipeline works, corpus not yet usable** (`scripts/attack-lab/{labeling,runner}.py`): with `kbd` in observe-only mode (temporary override, removed automatically and verified gone afterwards) the 6-scenario smoke test captured 10,080 events, 0 stream gaps, 6 executions, with the sensor and `kbd` stable. Findings: (1) the runner's 50 ms `/proc` poll missed short-lived children (`sudo cat /etc/shadow` lives ~10 ms), leaving 33 of 10,080 events attributed; `labeling.expand_pids` now adds every process whose `ppid` chain leads into the execution's tree within its window (33 -> 134 attributed events, `credential_access` 0 -> 33); (2) the audit export failed because the Python gRPC stubs in `kb-aads/comms` predate `ExportAuditLog`; the runner now uses `kbctl audit export`. **Open, and important for the evaluation:** `kbd`'s event feed only carries a process once the sensor syncs its state (every 20 events, or on a zone change), and the exit message is not republished as a `process_state`, so very short-lived or low-activity processes (compiler children, the process-injection and memory-exploit payloads) produce **no observation at all**: 3 of 6 executions have 0-1 attributed events. A sensor change (publish a final `process_state` on exit, rate-limited/configurable so a process storm does not overload `kbd`) is needed before a corpus can represent those scenarios. Also observed: the 8x RWX `mmap` payload scored only 12.5 (SAFE), a detection gap, not a capture problem. Not done: a full-size capture.
- **Attack-lab scenario runner and `KB_OBSERVE_ONLY` mode for `kbd`** (`scripts/attack-lab/{payloads,runner,capture,labeling}.py`, `kb-control-plane/internal/controlplane/controlplane.go`, `scripts/attack-lab/README.md`): first step of the sensor-derived training corpus (plan: `docs/development/control-aads/learned-policy-retraining.md`). The runner executes 12 scenarios (6 attacks incl. a low-and-slow evasion, 6 benign incl. `benign_admin_privileged` hard negatives that read `/etc/shadow` and use `sudo` legitimately), one execution at a time in seeded-shuffled order, while recording `kbd`'s `StreamEvents` feed. Ground truth is kept apart from telemetry (`events.jsonl` vs `labels.jsonl`, with per-execution pid trees, windows, first malicious action and what `kbd` audited for those pids); `labeling.py` builds execution-level, family-held-out splits with a leakage assertion. Safety: loopback-only network (tested), scratch-dir files, no exploit code, `--ack-isolated` required, refuses to run as root. **New `kbd` opt-in `KB_OBSERVE_ONLY=1`** (default off; the docs define no such mode, so this is an addition, not a change of documented behaviour): policy-driven containment (BORDERLANDS CGROUP throttle, `auto_terminate`, exfil auto-NAMESPACE) is replaced by `OBSERVE_ONLY_WOULD_<ACTION>` audit entries, with a startup warning; operator `SetContainment`/dashboard/`kbctl` and agent `SubmitAgentDecision` still enforce. The runner refuses to capture unless `kbd` is in this mode (or `--allow-containment`), because live containment truncates attacks and would teach a model "attacks that were already contained". Bugs found by its tests/smoke run and fixed: a `Thread._stop` name clash in the process-tree watcher, and a capture that reported "connected" before gRPC had connected (the run recorded 0 events for a user outside the `kb` group; it now fails fast). Tests: 11 lab tests (no root/gRPC) and 3 Go tests (both modes, operator containment unaffected). Smoke-tested end to end on the dev VM only after this entry's first draft; see the next entry for the result.
- **The sensor crashed `tailscaled` and froze the dev VM: Go TLS uprobes were attached at the wrong offset** (`kb-core/userspace/sensor/elf_symbols.{c,h}` (new), `kbd_sensor.c`, `Makefile`, `tests/test_elf_symbols.c`): `find_elf_symbol_offset()` returned the symbol's `st_value`, a VIRTUAL ADDRESS, but `bpf_program__attach_uprobe()` needs a FILE OFFSET. They coincide for PIE binaries and most libraries, but not for static non-PIE executables, which is how Go builds `tailscaled` (text at 0x400000: vaddr 0x612c00, real file offset 0x212c00, verified with `readelf` on the VM's `tailscaled` 1.98.4). The breakpoint therefore landed 4 MB away inside unrelated code; `tailscaled` crashed (SIGSEGV at `pc=0xa12bfd`, beside the probe site 0xa12c00; the crash seen since the first day), systemd restarted it, the sensor probed it again (twice per start), and the loop ended with the guest frozen (last journal lines of the frozen boot: `tailscaled ... status=2`, then two `[TLS DETECTOR] ... Attaching uprobe` for the new PID). Now: the lookup translates through the PT_LOAD program headers, requires a FUNCTION symbol inside an executable segment and returns 0 (do not attach) otherwise; the same pid is never probed twice; `KB_TLS_GO_UPROBE=0` disables Go TLS probes. The same lookup serves the OpenSSL/GnuTLS/NSS probes, which benefit too. **Verified:** unit test builds a static non-PIE fixture and checks the offset against the section headers (vaddr 0x402f75 -> file offset 0x2f75), PIE, data-symbol, missing-symbol and non-ELF cases pass; the new code returns 0x212c00 for the VM's real `tailscaled` (read-only run, nothing attached). **Verified on the dev VM after the freeze** (final build, capped throwaway units, real service still masked): with Go probes off, a 20 s process storm gave 0 dropped events on a cold start, 19-20% of a core, ~13k events/s processed, slowest entropy scan 116 ms (was 3-4 s), and an `/etc/shadow` read still reached SUSPICIOUS; with Go probes ON, `tailscaled` was restarted 4 times, survived every one (`NRestarts=0`, no SIGSEGV, load < 0.6) and was probed once per process at the correct offset 0x212c00 (the old sensor used 0x612c00). **Not verified:** the freeze mechanism itself (kernel-side) is inferred from the timing and journal, not observed; no soak longer than a few minutes. The laptop's sensor (old code) probed the Nix `go` binary 6 times at the wrong offset (static non-PIE, 0x7146c0 instead of 0x3146c0) without an observed crash.
- **Sensor overload: five root causes found and fixed (uncommitted at the time of writing; see verification status)** (`kb-core/userspace/sensor/kbd_sensor.c`, `userspace/behavior/{kb_scoring,kb_evidence,kb_behavior}.c`, `userspace/bridge/kb_bridge.c`, `tests/test_tables.c`): on a busy desktop host 1.1.0 used 92% of a core and dropped ~3,000 events/s (ring buffer full). Profiling on the dev VM under a synthetic process storm found: (1) the full-map entropy scan ran every 10 *polls*, and polls return immediately under load, so it ran every few ms; it is now time-based with a 10% duty cap, and the CWP orphan sweep likewise; (2) the scan took 0.5-4 s (blocking the consumer while the 1 MB ring buffer overflowed) because of an O(n^2) per-pid delta loop and 3 syscalls per map entry: now one pass plus batched `bpf_map_lookup_batch` (per-entry fallback kept); (3) every exec parsed the new process's ELF twice for Go TLS symbols: now cached by (dev, inode, size, mtime) after one `stat`; (4) the scoring, evidence and behavior tables (and the scan's four helper tables) probed linearly over the whole table with `pid % N`, so sequential pids and stale entries from lost exit events made every lookup O(table) (evidence lookup alone was 43-55% of CPU); they are now scatter-hashed, probe at most 64 slots and evict the least-evidenced/lowest-zone entry when the window is full, with a periodic reap of dead pids and a per-pid-table eviction counter in the 30 s summary; (5) **crash bug**: when the behavior table was full, `kb_behavior_evaluate()` returned no record and `process_behavior_and_score()` dereferenced it (SIGSEGV exactly under overload, a likely cause of the old "sensor restarts under overload"); now guarded and counted as "events left unscored". Also: one `write()` per frame to `kbd` instead of two; "ring buffer full" reports limited to one per 10 s with an accumulated count. **Measured on the Ubuntu 24.04 dev VM, same 20 s storm (6 parallel loops of short-lived processes):** dropped events 138,666 -> 0 on a warm second storm (13,478 on the cold first), sensor CPU 97% -> 19-29% of a core, no crash across repeated storms. **Not verified:** the final version (adds bounded probing to the four scan-side helper tables, which an earlier build showed still stalling a scan for 3-4 s) was built but not run on the VM because the VM lost its network; detection after these changes (`/etc/shadow` read reaching SUSPICIOUS) was not re-checked on the final build; no soak run; the host's own sensor still runs the old code. Table regression tests (`kb-core/tests/test_tables.c`) pass locally; they were not run against the old tables, whose behaviour was established by profiling.
- **Sensor journal feedback loop (critical)** (`kb-core/userspace/sensor/kbd_sensor.c`, `packaging/systemd/kb-sensor.service`): `handle_event` `printf`ed every ring-buffer event to stdout, which under systemd is the journal. journald's (and sshd's) own file and socket activity produced new events, which produced new lines: about 50k lines in two minutes on a guest, starving it (the `tailscaled` SIGSEGV loop is believed to be a consequence of the frozen guest, not verified). Per-event text is now off by default (`KB_SENSOR_VERBOSE=1` enables it, capped at 200 lines/s by a token bucket), the sensor skips events from its own PID, and a single summary line is printed every 30 s (seen/logged/suppressed/self-skipped). The unit also sets `LogRateLimitIntervalSec=10s`/`LogRateLimitBurst=200` as a backstop. Telemetry to `kbd` and scoring are unchanged. `[BEHAVIOR ENGINE]` state-transition lines are capped at 20/s too (the remainder counted in the summary). **Verified on the Ubuntu 24.04 dev VM** (2026-10-29, guarded transient unit: 60% CPU, 768 MB, journald rate limit, 50-60 s): ~45 s under a 400-process burst wrote 156 journal lines (8,258 events seen, 670 transition lines suppressed, 1,517 own-PID events skipped) against ~50k lines in 2 minutes before; sensor used ~14% CPU and 10 MB. The real `kb-sensor.service` was left masked by the operator and was not started. Installed over the 0.1.0 `.deb` files in `/usr/bin` (originals in `/var/backups/kb-20261029/`). End-to-end on the same VM: CGROUP then TERMINATE of a disposable process through `kbctl` applied (sensor logged both levels, victim killed after the ack arrived over `kbct.sock`, both audited). Not exercised live: refusal of a protected target (the one tried, `kbd`'s own PID, was untracked and rejected earlier with NotFound), a long-duration soak, and the tailscaled crash cause.

- **Learned policies could not work on live data (train-serving skew)** (`kb-aads/features/schema.py`, `consensus/jje.py`, `agents/containment.py`, `agents/hunter.py`, `config/agents.yaml`, `docs/development/control-aads/learned-policy-retraining.md`): the shipped Jury/Containment PPO checkpoints take a scenario `event_type` derived from the training labels, which `kbd` never emits; probed directly, a score-92 root BORDERLANDS process gets ALLOW/NONE with `event_type=0` and CONTAIN with a scenario code. A versioned feature contract (schema v1) now exists; checkpoints without a matching `feature_schema.json` are refused (override `KB_ALLOW_LEGACY_POLICY=1`, research only); the live Hunter uses deterministic levels and the Jury threshold vote unless `policy.use_learned` is set (default false). `kbd` now exports all six sensor dimension scores, `event_count` and `feature_schema` in `process_state` event metadata. **The 84.4% / 0% under-containment figures in `marl/README.md` are offline numbers on a leaky table and are not live performance.** Retraining on a sensor-derived corpus is not done; plan and gates are in the new doc.
### Added
- **Live agent decision pipeline** (`kb-aads/pipeline/flow.py`, `agents/ingest.py`, reworked `agents/hunter.py`, `consensus/jje.py`, `swarm/orchestrator.py`): closes `docs/development/control-aads/kb-events-swarm-ingestion-gap.md`. `IngestAgent` streams kbd `StreamEvents` (own client, reconnect with backoff), translates events, coalesces per PID in a bounded buffer (spikes kept, lowest score shed first, all counted) and feeds Patrollers; Hunter re-reads current state from kbd, derives confidence, asks the PPO Containment agent for a level (advisory), and submits to the Judge under a per-PID dedup/cooldown and concurrency cap; the Judge's rounds have a deadline and outcome counters; a level policy keeps TERMINATE to BORDERLANDS at confidence >= 0.85 whatever the model says. The swarm is advisory: kbd's deterministic enforcement never waits on it.
- **`internal/logx`**: keyed log rate-limiter ("+N similar suppressed"), applied to per-event lines in `controlplane.go` (zone transitions, process exits, stale-PID skips, store errors). Security lines (containment refusals, tamper, chain breaks) deliberately not limited.

## [1.0.0] - 2026-10-28

First release (the earlier `v0.1.0` was a pre-release). Version bumped to 1.0.0 in `packaging/arch/PKGBUILD`, `packaging/deb/build-deb.sh`, the `kbd` banner and the field manual (`latex/field-manual`, both editions rebuilt, 127 pages, CLI reference regenerated from the 1.0.0 binaries). `dist/` now holds the 1.0.0 Arch package (built on Arch) and `.deb` (built in an Ubuntu 24.04 container so it links glibc 2.39), the two manuals and `SHA256SUMS`; the 0.1.0 packages were removed from `dist/` (they remain attached to the `v0.1.0` GitHub pre-release). Internal Rust crate versions (`kb-checker`, `kb-tui`) are unchanged. Not exercised on a live host: the kill gate, the sensor ack and the dashboard Kill button (see the entries below); the `packaging/vm-test` run on the Ubuntu VM is still to be done with the 1.0.0 `.deb`.

### Changed
- **TERMINATE now really kills the process, behind CPM and CWP in `kbd` and in the sensor** (`kb-control-plane/internal/enforcement/enforce.go`, new `guard.go`): after `Enforcer.Contain` has sent a level-4 command to the sensor (which records level 4 in `contained_pids_map`), `kbd` sends `SIGKILL` to the PID. The sensor's own comment ("combined with the userspace SIGKILL sent by the enforcer") and `internal/enforcement/README.md` already described this; the code never did it. **The sensor's CPM/CWP gates refuse silently** (`kbd_sensor.c`, `cpm_classify`/`cwp_classify`: "Containment Prevented", no reply), and `Contain` returns success once the frame is written, so a kill sent only on that success would have bypassed both gates (found in review right after the first version of this change was pushed in `0264789`). `kbd` therefore applies the same rules itself **before** sending level 4 and before killing, and fails closed: PID 1; kernel threads (stat `PF_KTHREAD`, or no resolvable `/proc/<pid>/exe`); the protected-executable list (the sensor's compiled-in floor plus `/usr/bin`, `/usr/sbin` and the CPM.md §5.2 component paths, matched on the sensor's 63-byte key, also for a `(deleted)` binary); and CWP workloads from the loaded registry (path tier: protected; hash tier: protected only if the SHA-256 of the running image matches, a mismatch is logged as a security event and not exempted, a missing hash or a hashing failure is protected). The target is pinned with `pidfd_open`, classified through `/proc`, liveness-checked with signal 0 and killed with `pidfd_send_signal`, so a recycled PID cannot be hit. A refused TERMINATE sends nothing to the sensor. `ESRCH` after the send counts as success; other kill errors are returned. The existing PID-1 / self / protected-comm gate still runs first. This applies to every TERMINATE caller: gRPC `SetContainment`, the AADS executor, `policy:auto_terminate` and `kbctl process isolate --level TERMINATE`. Known limit: `kbd` mirrors the sensor's rules but cannot read its live `protected_pids_map`; making the sensor report its decision back to `kbd` would close that. `golang.org/x/sys` is now a direct dependency. Tests replace the target (`prepareTerminate`) for the whole package so no test can signal a real PID; the real `pidfd` path is tested against a child process the test owns.
- **Sensor CPM protected-executable list now includes the packaged install paths** (`kb-core/userspace/sensor/kbd_sensor.c`, `populate_protected_exec_paths`): the list only had `/usr/local/bin/...` for the KB programs, but `make install-pkg PREFIX=/usr` (the `.deb` and Arch packages) installs to `/usr/bin` (`/usr/sbin` is a symlink to it on those distros), so the sensor's exec-path check did not recognise `kbd`, `kbopd`, `kbagents`, `kbctl` and the others on a packaged host (the sensor itself was covered by its own PID registration). Added `/usr/bin/{kb-sensor,kb-checker,kbd,kbd_sensor,kbagents,kbopd,kbopt,kbctl}`, `/usr/sbin/{kbctl,kbd,kbd_sensor}` and `/usr/local/bin/kbd_sensor`, identical to `cpmProtectedExecPaths` in `internal/enforcement/guard.go` (26 of the map's 64 slots in use). Compiles (built in a scratch copy); not exercised against a running sensor, and the installed package keeps the old list until rebuilt.
- **The sensor now reports its CPM/CWP decision back to `kbd`; TERMINATE kills only on "applied"** (wire contract, additive: new `msg_type = 10 CONTAINMENT_ACK`, sensor to `kbd` on `kbd.sock`; `kb-core/userspace/bridge/kb_bridge.{h,c}`, `kb-core/userspace/sensor/kbd_sensor.c`, `kb-control-plane/internal/ipc/{types,wire}.go`, `internal/enforcement/acks.go`, `enforce.go`, `internal/controlplane/controlplane.go`, `docs/development/core-control/wire-protocol.md`): the sensor's CPM and CWP gates refuse silently, so after the Go-side gate there was still one way a protected process could be killed, namely a process only the sensor knows is protected (its live `protected_pids_map`). The sensor now answers every containment command with `{pid, level, decision}` (applied, CPM kernel thread / PID 1 / protected PID / protected executable, CWP path / hash, map update failed). `Enforcer.Contain` registers for the reply, sends level 4 and SIGKILLs only on "applied"; a refusal, a missing ack (3 s timeout) or an unknown decision means no kill and an error that names the sensor's reason. Acks are matched on `(pid, level)` (the command has no sequence number, and its layout is deliberately unchanged), so a pid whose TERMINATE went unanswered is locked out for 30 s. `ControlPlane.OnContainmentAck` audits every non-applied decision as `CONTAINMENT_REFUSED_BY_SENSOR` (CPM.md §2.5). Compatibility: `KB_WIRE_VERSION` stays 3; a `kbd` without this change ignores the new message. **A sensor that predates this change never acks, so TERMINATE (including the dashboard Kill button) is refused with "sensor did not acknowledge" until the sensor is rebuilt and reinstalled.** Sensor C code compiles (built in a scratch copy); the end-to-end path (real sensor, real ack, real kill) is not exercised, it needs root. [Teju, Pardhu]
- **Dashboard: Kill is separate from Isolate** (`kb-control-plane/internal/controlplane/http.go`, `kb-op/kb-dashboard/src/App.tsx`, `index.css`): `POST /api/isolate` used containment level TERMINATE, so with the change above it would have killed. It now uses NAMESPACE (level 3: network, exec and executable-memory operations denied, reversible with `/api/restore`) and audits `SET_CONTAINMENT_NAMESPACE`. New `POST /api/kill` (same bearer token) contains at level 4 and SIGKILLs, audits `KILL_PROCESS`. The dashboard gets a Kill button next to Isolate/Restore with an inline two-click confirmation (first click arms it for 4 s). Both routes now return 502 with `{"success":false,"error":...}` when containment is refused or fails (protected process, no sensor connected, kill failed); previously the result was ignored and `success:true` was always returned. Not exercised against a live sensor (needs root); unit tests cover the wire level, the failure paths and the method check. Field manual API table updated; the dist PDFs were not rebuilt. [Pardhu, Teju]

## Incident: `sudo`/PAM lockout during live LSM-block verification (2026-07-17)

**What happened**: While verifying the zero-padding fix (see Fixed above), the LSM sensitive-path block fired correctly for the first time in this repo's history — and immediately blocked reads of `/etc/sudoers` and `/etc/shadow` system-wide, because the block was unconditional (applied to every process, not just contained ones) at the time this was tested. This broke `sudo` itself (`sudo: unable to open /etc/sudoers: Permission denied`) and PAM password authentication generally (`su`, `pkexec`, `login` — anything reading `/etc/shadow`) on the live test VM.

**Why recovery was hard**: Every standard privilege-escalation path needs one of the two now-blocked files: `sudo` reads `/etc/sudoers` on every invocation; PAM's `pam_unix` module reads `/etc/shadow` to verify a password, so even `pkexec` (a different authorization mechanism) failed at the PAM step. With no already-authenticated root shell or key-based root SSH login available, the only recovery path left was a full VM restart from outside the terminal (hypervisor/cloud console) — a reboot clears all BPF programs, including the stuck LSM hook, since they don't persist across boots.

**Root cause**: `kb_lsm_file_open`'s sensitive-path check was unconditional — it applied to every process on the system, not scoped to processes an operator had actually placed into containment. This was inconsistent with the containment-level model the code's own comments already documented (`kb-core/ebpf/kbd_sensor.bpf.c`'s "Containment level semantics" block says sensitive-path blocking belongs to level-2 containment) and inconsistent with every other LSM hook in the same file, all of which are already containment-gated.

**Resolution**: Made `kb_lsm_file_open` containment-gated, matching the rest of the file (see Changed above). Verified post-fix: `sudo whoami` succeeds cleanly with `kbd_sensor` actively running and enforcing; a deliberately-contained test process has its sensitive-path access blocked as intended, while every other process is unaffected.

**Takeaway for future work on this hook**: any change to `kb-core`'s LSM blocking logic should be tested by containing a *disposable* test process first, never verified by directly triggering system-wide "does the floor list block this path" checks against real `/etc/sudoers`/`/etc/shadow` on a machine you still need `sudo` on.
